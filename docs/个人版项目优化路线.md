# 2. P0：稳定性与生命周期治理

## 2.1 修复 XSS 面板未完整清理的定时器

### 涉及文件

- `src/panels/xss/XssPanel.svelte:368-389`
- `src/panels/xss/XssPanel.svelte:796`

### 当前问题

`runIntercept()` 会创建轮询 `setInterval` 和约 8 秒的 `setTimeout`。用户快速切换面板或关闭侧栏后，旧回调仍可能执行，并继续修改：

- `intercepting`
- `capturedAjax`
- `interceptMsg`

这可能造成：

- 已卸载组件继续回写状态；
- 多次启动后存在多组 Timer；
- 页面注入的拦截逻辑比 UI 生命周期更长；
- 旧任务结果覆盖新任务状态；
- 长时间使用后 Timer 和监听器数量缓慢增长。

### 实现步骤

1. 在组件顶层保存所有 Timer 句柄：

   ```ts
   let interceptPollTimer: ReturnType<typeof setInterval> | undefined;
   let interceptStopTimer: ReturnType<typeof setTimeout> | undefined;
   let runEpoch = 0;
   ```

2. 新增幂等清理函数：

   ```ts
   function clearInterceptTimers() {
     if (interceptPollTimer !== undefined) {
       clearInterval(interceptPollTimer);
       interceptPollTimer = undefined;
     }

     if (interceptStopTimer !== undefined) {
       clearTimeout(interceptStopTimer);
       interceptStopTimer = undefined;
     }
   }
   ```

3. 每次启动前先调用一次清理函数，避免重复启动叠加。
4. 每次启动递增 `runEpoch`，异步回调提交结果前检查 epoch 是否仍一致。
5. 停止操作中同时：
   - 清理 Timer；
   - 停止页面侧拦截；
   - 更新 UI 状态；
   - 使旧 epoch 失效。
6. 在 `onDestroy()` 中调用统一停止函数。
7. `src/panels/xss/XssPanel.svelte:796` 附近的 3 秒 delay 改为可取消 delay，或在 delay 返回后检查 epoch/AbortSignal。

### 验收标准

- 连续进入和离开 XSS 面板 100 次，活动 Timer 数量不持续增长。
- 拦截运行期间切换面板，8 秒后不会出现旧面板状态更新。
- `启动 → 停止 → 再启动` 不会收到重复结果。
- 组件卸载后页面侧拦截器被恢复。
- 控制台无组件卸载后更新、未处理 Promise 或重复监听警告。

## 2.2 修复 Vue 面板页面拦截器恢复不完整

### 涉及文件

- `src/panels/vue/VuePanel.svelte:109-218`
- `src/panels/vue/VuePanel.svelte:273-281`

### 当前问题

权限拦截功能会在页面 MAIN world 中包装原生 `fetch` 和 XHR。当前停止流程主要调用 `P.stop()` 并清理侧栏轮询，但没有保证调用 `P._restore()`。

可能结果：

- 用户关闭面板后，页面的 `fetch`/XHR 仍被包装；
- 重复启动可能复用旧的全局对象；
- 多次启动、停止后出现包装层叠加；
- 页面行为受到长期影响；
- 调试时难以判断问题来自目标页面还是扩展残留。

### 实现步骤

1. 把停止流程收敛为单一 `stopPermIntercept()`，所有退出路径都调用它。
2. 在目标 Tab 的 MAIN world 中执行：
   - `P.stop()`；
   - `P._restore()`；
   - 删除或重置挂在 `window` 上的全局对象；
   - 清空内部队列和标志位。
3. 页面恢复操作必须幂等：调用两次不会报错，也不会再次替换函数。
4. 清理 side panel 中的轮询 Timer。
5. 每次启动前检查是否有旧实例，有则先恢复再安装。
6. 在 `onDestroy()` 中调用停止流程。
7. 对 Tab 关闭、页面刷新、脚本执行失败分别容错，避免清理失败阻塞 UI。

### 验收标准

在测试页面保存：

```js
const originalFetch = window.fetch;
const originalOpen = XMLHttpRequest.prototype.open;
```

然后验证：

- 开启拦截后引用发生变化；
- 停止后恢复为原始引用；
- 重复 20 次启动/停止，不出现多层包装；
- 关闭面板后页面请求行为恢复正常；
- 页面全局对象不残留旧结果和 Timer。

## 2.3 建立统一的组件任务生命周期

### 涉及文件

- `src/lib/tasks/task-controller.ts:105-132`
- `src/panels/multiurl/MultiurlPanel.svelte:75`
- `src/panels/xss/XssPanel.svelte:796`
- `src/components/scanner/UrlInput.svelte:98`
- 其他包含 `setTimeout`、`setInterval`、长 Promise 链的面板

### 目标

让所有长任务具有一致的四种状态和三种生命周期操作：

```text
idle → running → success/error/cancelled
start → cancel → dispose
```

### 推荐接口

```ts
interface PanelTaskContext {
  signal: AbortSignal;
  taskId: number;
  isCurrent(): boolean;
}
```

每个任务必须遵守：

1. 启动新任务会取消旧任务。
2. 网络请求接收 `AbortSignal`。
3. 延时和轮询可取消。
4. 任务结束前检查 `isCurrent()`。
5. 组件卸载调用 `dispose()`。
6. 取消不是错误，不应显示失败 Toast。
7. 旧任务不能覆盖新任务结果。

### 可取消 delay 示例

```ts
export function abortableDelay(ms: number, signal: AbortSignal): Promise<void> {
  return new Promise((resolve, reject) => {
    if (signal.aborted) {
      reject(signal.reason);
      return;
    }

    const timer = setTimeout(resolve, ms);
    signal.addEventListener(
      'abort',
      () => {
        clearTimeout(timer);
        reject(signal.reason);
      },
      { once: true },
    );
  });
}
```

### 验收标准

- 所有有“停止/取消”按钮的任务在 200ms 内停止启动新工作。
- 取消后 UI 不进入成功状态。
- 快速连续启动 10 次，只显示最后一次结果。
- 面板卸载后无任务继续更新 Svelte 状态。
- 单元测试覆盖成功、失败、取消、旧任务回写四种路径。

## 4.1 为 ResponsiveTable 增加统一分页

### 涉及文件

- `src/components/results/ResponsiveTable.svelte:64-100`
- `src/panels/storage-check/StorageCheckPanel.svelte:590-658`
- `src/panels/source-loader/SourceLoaderPanel.svelte:259`

### 当前问题

`ResponsiveTable` 会完整渲染所有行，窄屏 card 模式同样如此。部分面板还会递归渲染 IndexedDB/store/record。数据达到数千条时，DOM 数量、布局、内存和更新成本会线性增长。

### 推荐两阶段方案

#### 第一阶段：分页

先实现通用分页，风险低且容易推广：

- 默认每页 50 条；
- 支持 50/100/200；
- 显示总数和当前范围；
- 上一页、下一页；
- 搜索/排序后自动回第一页；
- 导出仍使用完整数据；
- 使用稳定业务 key。

建议接口：

```ts
interface PaginationOptions {
  page: number;
  pageSize: number;
  total: number;
  pageSizeOptions?: number[];
}
```

#### 第二阶段：虚拟列表

当结果大于 1,000 条时启用虚拟化：

- DOM 行数维持约 100～150；
- 支持 overscan；
- 尽量固定行高；
- 宽屏 table 和窄屏 card 分别配置行高；
- 保持选择、展开和键盘焦点状态。

### 验收标准

- 10,000 行时 DOM 节点不超过约 150 个结果项。
- 滚动帧率目标 ≥ 55 FPS。
- 首次渲染无明显长任务。
- 搜索、排序、翻页后焦点行为合理。
- 导出数量等于完整结果，而不是当前页数量。

# 5. P1：并发、取消与数据处理性能

## 5.1 Gather 脚本抓取增加并发池

### 涉及文件

- `src/panels/gather/GatherPanel.svelte:255-256`

### 当前问题

当前使用 `Promise.all` 同时请求所有同源脚本。资源较多时会造成：

- 短时大量并发；
- 内存峰值；
- UI 进度不平滑；
- 点击取消后难以及时停止；
- 单个失败可能干扰整体错误处理。

### 推荐实现

建立共享工具：

```ts
mapWithConcurrency<T, R>(
  items: T[],
  concurrency: number,
  worker: (item: T, index: number, signal: AbortSignal) => Promise<R>,
  signal: AbortSignal,
): Promise<R[]>;
```

配置建议：

- 默认并发 6；
- 可根据需要在 4～8 之间调整；
- URL 先去重；
- 限制最大处理资源数；
- 每完成一个任务更新进度；
- 单个失败记录为结果，不立即终止全部；
- 用户取消后不再调度新任务。

### 验收标准

- 100 个资源时，同时在途请求不超过设定值。
- 取消后不再启动新请求。
- 进度值单调递增且最终正确。
- 失败资源不会导致已成功结果丢失。

# 7. P2：面板加载和切换体验

## 7.1 缓存 loader Promise

### 涉及文件

- `src/entrypoints/side-panel/App.svelte:172-188`
- `src/panels/loaders.ts:13-60`

### 当前情况

动态 import 分 chunk 已经正确，不需要重写。浏览器也会缓存模块，但 `currentPanel.load()` 的 Promise 和加载状态仍可在应用层复用，使反复切换更稳定。

### 实现方案

```ts
const panelPromiseCache = new Map<PanelId, Promise<PanelModule>>();

function loadPanel(id: PanelId) {
  let promise = panelPromiseCache.get(id);
  if (!promise) {
    promise = loaders[id]();
    panelPromiseCache.set(id, promise);
    promise.catch(() => panelPromiseCache.delete(id));
  }
  return promise;
}
```

注意：加载失败后必须删除缓存，否则重试会永远拿到 rejected Promise。

### 选择性预加载

只预加载高概率下一步使用的面板：

- Sidebar hover/focus 后延迟 100～200ms；
- 浏览器 idle 时预加载常用面板；
- 不要启动时预加载全部 35 个面板。

### 验收标准

- 同一面板加载成功后再次切换不会重新显示长时间 loading。
- 加载失败后点击重试可以重新发起 import。
- 首屏网络请求数量不因预加载策略明显膨胀。

## 7.2 谨慎处理面板重挂载

### 涉及文件

- `src/entrypoints/side-panel/App.svelte:172-188`

当前使用类似：

```svelte
{#key `${activePanel}-${loadNonce}`}
```

切换面板会销毁并重建组件。这有两个面向：

- 优点：面板状态和监听器容易隔离；
- 缺点：切回来后本地状态丢失，重型初始化重复执行。

### 推荐策略

不要直接把所有面板改成 keep-alive。先分类：

1. **无状态/轻量面板**：继续销毁重建。
2. **有长输入或昂贵结果的面板**：把必要状态提升到 store 或 session cache。
3. **运行中任务面板**：切换时明确取消，或由 TaskController 托管。
4. **仅需恢复输入的面板**：只缓存输入和筛选条件，不缓存完整 DOM。

### 验收标准

- 面板切换不会保留失控 Timer。
- 重要输入在合理范围内可恢复。
- 不通过隐藏全部面板 DOM 的方式实现 keep-alive。

1. 增加 `clean:inject`。

6. 额外验证 TS basename 集合与 JS basename 集合完全一致。

### 验收标准

- 干净 checkout 构建后正好 11/11 对应。
- 删除一个 TS 后重新构建，不残留对应 JS。
- dev server 运行期间修改 TS，对应 JS 自动更新。
- CI 能发现忘记提交生成物的情况。

# 16. 明确不建议做的事情

1. **不建议重写整个项目或更换 Svelte/WXT。**
2. **不建议重写 registry/loaders。** 当前架构已验证有效。
3. **不建议把所有面板常驻 DOM 来实现状态保留。** 会增加内存和监听器风险。
4. **不建议一开始给所有列表上复杂虚拟化。** 先分页，再处理真正的大列表。
5. **不建议只追求覆盖率数字。** 优先覆盖复杂分支和高回归模块。
6. **不建议一次性开启 inject 全部 strict 规则。** 应分步收紧。
7. **不建议一次修改数十个面板。** 每批 3～5 个，便于发现回归。
8. **不建议继续复制面板内下载、Timer、并发和状态逻辑。** 应先完善公共基础设施。
9. **不建议重复建设 Toast、UrlInput、reduced-motion 等已有成熟能力。**
10. **不建议在完成 P0/P1 前继续大量增加新面板。**

---

# 17. 最终推荐顺序

如果只保留最重要的非安全工作，建议严格按照以下顺序执行：

1. 修复 XSS/Vue 拦截器和 Timer 生命周期。
2. 建立统一取消、dispose 和旧结果防回写机制。
3. 修复 coverage 命令并建立 CI。
4. 修复 Source Map 测试警告。
5. 为 ResponsiveTable 和大结果面板增加分页。
6. 给 Gather 增加有限并发和取消。
7. 补 sender-guard、crypto、scanner、fetchers 等复杂模块测试。
8. 统一下载 helper 和 Object URL 回收。
9. Payload 按类别动态加载并优化过滤。
10. 修复 analysis-context 并发消费。
11. 建立 inject clean/watch/CI 同步检查。
12. 固定 Node/pnpm 并统一版本号来源。
13. 完善 Sidebar combobox 和剩余表单可访问名称。
14. 最后再进行小范围重复代码清理和视觉细节优化。

完成前 8 项后，项目的长期稳定性、性能和可维护性会比继续增加面板功能获得更明显的提升。
