# 灵眸 权限矩阵 — 灵眸 v7.2

> 目的：为 manifest 中声明的每一项权限提供「功能、调用位置、是否必需、替代方案、风险与缓解」佐证，
> 满足最小权限原则与可审计性。新增功能扩大权限前，必须先更新本文件并在 PR 中说明。
>
> 对应源：`wxt.config.ts` manifest 段；最近一次审计：2026-07-13。

## 1. permissions（API 权限）

| 权限 | 功能 | 调用位置 | 是否可选 | 替代方案 | 风险 / 缓解 |
|---|---|---|---|---|---|
| `activeTab` | 用户点图标后获得当前 tab 的临时访问（content script 注入、tab 信息） | `core/tabs.ts`、各探测面板 | 必需 | 无 | 低；语义上即「用户显式授权当前页」 |
| `tabs` | 读取/查询 tab 列表与 URL（资产测绘、信息收集需当前页 URL，不限于点图标之后） | `core/tabs.ts:getActiveTabUrl`、`context-menus.ts` | 必需 | 仅靠 `activeTab` 无法在面板打开时被动获取 URL | 中：可读取所有 tab 的 URL。仅用于取当前活跃 tab，未遍历/外传 |
| `storage` | 持久化用户配置（API key、布局、扫描历史、HaE 规则、限流设置等） | 全局（`stores/*`、各面板） | 必需 | 无 | 低；敏感数据（API key）见 §3 生命周期策略 |
| `scripting` | 动态注入 content script / 执行页面脚本（RuoYi hook、右键 toast/复制、框架探测注入） | `background/ruoyi-hook.ts`、`background/context-menus.ts`、`core/messaging.ts`、`core/tabs.ts` | 必需 | 无 | 中；仅注入自有脚本，target 始终为用户当前 tab |
| `contextMenus` | 右键菜单（编解码、哈希、扫描入口） | `background/context-menus.ts` | 必需 | 无 | 低 |
| `declarativeNetRequestWithHostAccess` | 改写请求头（UA/Header 伪造）、阻断 JS（JS 控制面板） | `background/dnr.ts`、`panels/jsctrl`、`panels/spoof` | 必需 | 无 | 中；动态规则受 host_permissions 约束，仅作用于用户指定 origin |
| `cookies` | Cookie 审计面板读取/改写/删除目标域 Cookie；请求伪造面板的 Cookie 操作 | `panels/cookie-audit`、`panels/spoof` | 功能必需 | 可改为可选权限（用户启用 Cookie 审计时按需请求） | **高**：可读写目标域 Cookie。仅限用户在面板中显式填入的 domain；不外传、不写日志 |
| `sidePanel` | 侧栏（主交互入口） | `entrypoints/side-panel`、`context-menus.ts` | 必需 | 无 | 低 |

### 已移除

| 权限 | 原因 |
|---|---|
| `downloads` | **审计发现从未使用**。所有下载均通过 `<a download>` + `URL.createObjectURL(blob)`（`AssetPanel`、`JsArchivePanel`、`SourceLoaderPanel` 等），该模式不需要 `downloads` 权限。v7.2 移除以收敛权限面。 |

## 2. host_permissions

| 主机 | 功能 | 是否必需 | 风险 / 缓解 |
|---|---|---|---|
| `<all_urls>` | content script 注入（`bridge.content.ts` matches `<all_urls>`）、Cookie 审计、DNR 改写、JS 归档对任意目标页生效 | 必需（当前形态） | **高**：理论上可访问任意站点。缓解：(1) 所有跨域抓取走 background 代理 + `url-guard` SSRF 防护；(2) 无任何自动外传，操作均由用户在面板触发；(3) 未来若拆分为「按目标域按需授权」可进一步收敛 |

> **为何不能用 activeTab 完全替代 `<all_urls>`？** `activeTab` 仅在「用户点击扩展图标/快捷键/右键」后对**当前 tab** 临时授权。但 cookie 审计、JS 归档、框架分析需要扩展面板（独立上下文）在用户未与图标交互时也能读取页面（如面板已打开、用户在面板内填入域名）。故保留 `<all_urls>`，并依赖 url-guard + sender-guard 双重门控。

## 3. web_accessible_resources

| 资源 | matches | 是否必需 | 风险 / 缓解 |
|---|---|---|---|
| `inject/*.js` | `<all_urls>` | 必需 | 中：MAIN world 注入脚本须在用户分析的任意目标页加载。缓解：(1) 脚本仅暴露受 token 约束的回执通道；(2) `bridge.content.ts` 校验 `event.source === window` + 同源 + token + dataKey；(3) 注入脚本不接受任意 action，仅枚举白名单 |

## 4. content_security_policy

```text
extension_pages: "script-src 'self'; connect-src *; object-src 'self';"
```

| 指令 | 当前 | 评估 | 改进方向 |
|---|---|---|---|
| `script-src` | `'self'` | ✅ 严格，无远程脚本、无 `eval`（XSS 注入面小） | 保持 |
| `object-src` | `'self'` | 可进一步收紧到 `'none'`（扩展页面无插件需求） | 计划收紧 |
| `connect-src` | `*` | ⚠️ 偏宽。**但面板不直接 `fetch` 目标**（全量走 background 代理 + url-guard，见 §5），宽放主要兼容资产测绘外链平台等少量直接打开的外部资源 | 计划收紧到实际需要的域集合；用户输入的任意 URL 一律走 background fetch + url-guard，不依赖 `connect-src *` |

## 5. 网络请求统一策略（SSRF 防护）

- **单一入口**：所有目标抓取必须经 `sendMessage({type:'FETCH_*'}) → background`，禁止面板直接 `fetch`。审计确认 `src/panels/**` 无直接 `fetch` 调用。
- **url-guard**（`core/url-guard.ts`）：拦截非 http(s)、loopback（含 IPv6 `[::1]`）、私网段、链路本地、`.local/.internal`、纯数字主机名。
- **sender-guard**（`background/sender-guard.ts`）：按消息类型校验来源（扩展页面 / content script），未授权来源拒绝。
- **响应预算**：`fetchUrl` 流式读取，单响应硬顶 20MB、默认 5MB，超限返回 `TOO_LARGE`；JS 归档另有 100MB 累计预算。
- **速率限制**：`background/rate-limit.ts` 按 hostname 限流。
- **错误正文**：HTTP 错误体只回传 ≤200 字符摘要，避免回传巨大错误页或敏感头。

## 6. 敏感数据生命周期

| 数据 | 默认处理 |
|---|---|
| Cookie / Token / API key | 内存短暂使用；storage.local 存储（用户主动保存）；不写日志、不进下载归档；报告脱敏（`***REDACTED***`） |
| 页面 DOM / 内联脚本 | 仅保留用户主动导出的结果；JS 归档导出前提示可能含敏感信息 |
| 扫描历史 | 提供清理；`scan-history` 已做写放大优化，结果同窗合并 |
| JS 归档 MANIFEST | 不记录 Cookie / Authorization；仅记 url/path/size/status/source |
| 错误响应 | 仅保存有限长度摘要，过滤 `Authorization` / `Set-Cookie` |

## 7. 渲染安全（XSS）

- 审计确认 `src/**` 无 `{@html}` 使用，全部文本输出走 Svelte 文本绑定（自动转义）。
- 注入脚本回传数据经 token + origin/source 校验后才进入 UI。

## 8. 发布前检查（manifest diff）

发版前执行：

```bash
# 对比 manifest 权限变更，避免新功能无意扩大权限面
git diff <last-tag> -- wxt.config.ts
pnpm check   # 0 errors 基线
pnpm test    # 全绿基线
```

新增权限时必须：(1) 更新本矩阵；(2) 在 PR 说明必要性与是否可拆为可选权限；(3) 评估 host_permissions / web_accessible_resources 是否同步扩大。
